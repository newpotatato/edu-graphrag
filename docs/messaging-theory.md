# Messaging: ответы на теоретические вопросы

Примеры — из нашего конвейера: источник / `POST /api/v1/tasks` → RabbitMQ `tasks` → воркер → Postgres.

## 1. Команда vs событие. Когда event-driven оправдан

- **Команда** — просьба сделать что-то конкретное, адресована одному исполнителю, может быть
  отклонена: «классифицируй этот текст» (`TaskMessage`). Имя в повелительном наклонении.
- **Событие** — факт, который уже произошёл, отправитель не знает и не важно, кто подпишется:
  «задача выполнена», «документ загружен». Имя в прошедшем времени, отменить нельзя.
- Event-driven оправдан: несколько независимых потребителей одного факта, разная скорость
  частей системы (буфер), развязка по времени и доступности, аудит/воспроизведение истории.
- Избыточен: нужен синхронный ответ «здесь и сейчас», один потребитель и простая логика,
  маленькая система — брокер добавит задержку, инфраструктуру и сложность отладки.

## 2. Зачем брокер, если есть HTTP

Получаем: **развязку по времени** (воркер может лежать — сообщения ждут), **буферизацию и
сглаживание пиков**, **балансировку** между N воркерами без service discovery, **гарантии
доставки** (ack, повторы, DLQ), **backpressure** (ограниченная очередь сигналит продюсеру),
fan-out одному событию многим потребителям.
Платим: ещё одна система (эксплуатация, мониторинг, отказоустойчивость самого брокера),
**асинхронность** (нет немедленного ответа, нужен статус/поллинг), at-least-once → нужна
**идемпотентность**, сложнее трассировка и отладка, eventual consistency.

## 3. Маршрутизация в RabbitMQ. Очередь vs лог

- Продюсер публикует в **exchange** с **routing key**; **binding** связывает exchange с
  **queue** по правилу; потребители читают **queue**.
- Типы exchange: `direct` (точное совпадение ключа — наш `tasks`), `fanout` (всем
  привязанным — наш `tasks.dlx`), `topic` (шаблоны `a.*.c`, `#`), `headers`.
- **Брокер-очередь (RabbitMQ)**: сообщение удаляется после ack, брокер сам раздаёт сообщения
  потребителям (push, prefetch), умная маршрутизация, per-message ack, DLQ, приоритеты, TTL.
- **Брокер-лог (Kafka)**: append-only лог по партициям, сообщения хранятся по времени/размеру
  независимо от чтения, потребитель сам хранит offset (pull), можно перечитать историю,
  порядок — внутри партиции, масштабирование — числом партиций.

## 4. Как не потерять сообщение

- **Producer**: publisher confirms (ждать ack брокера) + `mandatory` (не потерять
  немаршрутизируемое) + повтор при nack/таймауте; для атомарности с БД — transactional outbox.
- **Брокер**: durable exchange/queue, persistent-сообщения (delivery_mode=2), реплицируемые
  **quorum-очереди** (Raft) вместо одной копии; confirm приходит только после записи на диск/кворум.
- **Consumer**: ручной/поздний ack — только **после** записи результата; при падении
  неподтверждённые сообщения возвращаются в очередь. Ограниченный prefetch.

## 5. ack / nack / reject

- **ack** — обработано, можно удалить. **nack** (`basic.nack`, можно пачкой) и **reject**
  (`basic.reject`, по одному) — не обработано; с `requeue=true` вернуть в очередь, с
  `requeue=false` — удалить или отправить в DLX.
- Когда ack: после того, как побочный эффект зафиксирован (у нас — после `COMMIT` результата в
  Postgres). Ack до записи = потеря при падении между ack и записью.
- Неподтверждённые сообщения: не видны другим потребителям, пока канал жив; при закрытии
  канала/соединения брокер возвращает их в очередь (redelivered=true, у quorum — растёт
  `x-delivery-count`). Число неподтверждённых на потребителя ограничивает `prefetch_count`.

## 6. Гарантии доставки. Exactly-once

- **at-most-once**: ack до обработки — без дублей, но возможна потеря.
- **at-least-once**: ack после обработки — без потерь, но возможны дубли (наш выбор).
- **exactly-once** в распределённой системе с ненадёжной сетью на уровне доставки
  недостижим (нельзя отличить «не дошло» от «дошло, но потерялся ack»). На практике под ним
  понимают **effectively-once / exactly-once processing**: at-least-once доставка +
  идемпотентный потребитель (или транзакционная связка чтения/записи, как в Kafka
  transactions внутри Kafka) — эффект применяется ровно один раз.

## 7. Идемпотентный потребитель

Повторная обработка того же сообщения не меняет результат. Способы:
- **уникальный ключ в хранилище** + upsert/`INSERT … ON CONFLICT` (наш: `task_id` — первичный
  ключ, `save_result` не перезаписывает уже `done`);
- **inbox-таблица** обработанных message_id в той же транзакции, что и эффект;
- естественно идемпотентные операции (`SET status = 'done'`, а не `count = count + 1`);
- версионирование / условные обновления (`WHERE version = …`).
Нельзя: «проверить, затем вставить» без уникального ограничения — гонка двух доставок.

## 8. Dual write, outbox, inbox

**Dual write**: сервис пишет в БД и публикует в брокер — двумя независимыми операциями; если
одна прошла, а вторая упала, состояния разошлись (запись без события или событие без записи).
- **Transactional outbox**: в одной транзакции с бизнес-данными пишем сообщение в таблицу
  `outbox`; отдельный релей доставляет его в брокер (at-least-once) и помечает отправленным.
- **Inbox**: на стороне потребителя в одной транзакции с эффектом записываем `message_id` в
  `inbox` (уникальный ключ) — дубль отсекается.
- У нас в API outbox намеренно не используется: при перегрузке нужно **немедленно отказать**
  (503), а outbox принял бы задачу «в долг». Вместо этого: транзакция `INSERT pending` →
  publish с confirm → `COMMIT` или `ROLLBACK` + 503.

## 9. Доставка из outbox: polling vs CDC. Почему не LISTEN/NOTIFY

- **Polling**: релей периодически `SELECT … FOR UPDATE SKIP LOCKED LIMIT n` неотправленных,
  публикует, помечает. Просто, но задержка = период опроса и нагрузка на БД.
- **CDC (Debezium и т.п.)**: читает журнал транзакций (WAL, logical replication), минимальная
  задержка, нет опроса, порядок коммитов; сложнее инфраструктура.
- **LISTEN/NOTIFY** не годится как транспорт: уведомления не персистентны (нет слушателя —
  потеряно), доставляются только подключённым, ограничен размер payload, нет подтверждений и
  повторов. Максимум — как «подсказка разбудить поллер», но не как гарантия.

## 10. Ошибки: повторы, задержки, DLQ, «ядовитые» сообщения

- Разделять **временные** ошибки (БД недоступна, таймаут) — повторять, и **постоянные**
  (невалидное сообщение) — не повторять.
- Повторы ограничены: у нас quorum-очередь с `delivery-limit` — после N доставок сообщение
  уходит в DLX → `tasks.dlq`. Бесконечный requeue «ядовитого» сообщения клинит очередь.
- Задержка между повторами (exponential backoff + jitter): через retry-очереди с TTL, плагин
  delayed-message или повтор внутри обработчика; немедленный requeue — проще, но повтор сразу.
- **Ядовитое сообщение** (poison) — то, которое падает при каждой обработке: у нас
  невалидный `TaskMessage` сразу `reject(requeue=false)` → DLQ; DLQ разбирается вручную или
  отдельным процессом, задача помечается `failed`.

## 11. Producer быстрее consumer. Backpressure, load shedding, rate limiting

Без ограничений очередь растёт неограниченно: растёт память брокера, время ожидания задачи
(закон Литтла: W = L / λ), в итоге memory alarm или OOM.
- **Backpressure** — сигнал о перегрузке идёт **назад по цепочке**, и источник **сам
  замедляется**: очередь ограничена (`max-length` + `reject-publish`), брокер nack-ает
  публикации, источник ждёт с backoff. Скорость источника = пропускная способность воркеров.
- **Load shedding** — сбрасываем лишнюю работу на границе, когда источник замедлить **нельзя**
  (внешний клиент): `POST /api/v1/tasks` сразу отвечает `503 + Retry-After`.
- **Rate limiting** — фиксированный лимит частоты (N запросов/с) независимо от реальной
  загрузки: защищает, но не адаптируется (то недогружает, то перегружает).

## 12. Порядок сообщений

- RabbitMQ сохраняет порядок внутри одной очереди для одного потребителя; при нескольких
  потребителях, prefetch > 1, повторах (requeue возвращает сообщение не на своё место) порядок
  обработки нарушается. Kafka — порядок внутри партиции.
- Гарантировать порядок для сущности: ключ партиционирования (все события одного объекта в
  одну партицию/очередь), один потребитель на партицию, последовательные номера/версии и
  отбрасывание устаревших, идемпотентные обновления.
- Глобальный порядок недостижим без отказа от параллелизма: он требует одной точки
  сериализации (одна очередь, один потребитель, prefetch=1), что убивает масштабирование и
  отказоустойчивость; часы разных узлов не синхронизированы, а сеть переупорядочивает сообщения.
